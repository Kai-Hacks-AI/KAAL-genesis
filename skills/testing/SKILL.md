# Testing

Testing establishes whether stated protection holds for a candidate. It knows three things, from the outside in, and leaves a fourth, Strategy, to the using system:

A **Plan** states a testing purpose and collects the Suites and Carriers that serve it. It is Markdown: YAML frontmatter, then a body. The body, which must not be empty, states what the Plan protects and why, for the people and agents who author and review it. The frontmatter's `suites` lists the Suites it collects, each a relative posix path to a Suite directory beneath the testing root, each at most once. It may also list `carriers`, each a relative posix path to a Case file beneath the testing root, each at most once, collected whether or not any Suite holds it; a Plan that collects only Carriers need not state `suites`, and one that states neither is refused. A Case that a Suite and the Plan both collect is one Case, and a Run executes it once. A `carriers` entry may instead be a mapping of a `carrier` and non-empty `parameters`, each a plain name with a plain string value, no whitespace and none of `,`, `=`, `[` or `]`: the Plan then requires what that Carrier carries **under those parameters**. What is instantiated is the HOW, a Test Case, never the Carrier: a **required instance** is a Test Case under parameters, and the same Test Case may be required under several sets of them. Testing can name only the file that executes a HOW, and a Run performs it whole, so today an instance is named by the Carrier that holds the Test Case and its parameters, and every Test Case in that Carrier is instantiated with it. That is the Runner's projection and its limit, not what an instance is: that Test Cases share a file says nothing about whether they are parameterized together, and no later way of selecting a Test Case changes what an instance means. Each distinct Carrier with its parameters, their order meaning nothing, is one instance the Plan requires, and one required twice, however it is stated, is one. An instance under no parameters is a Carrier collected as a Case always was, and its identity is the Carrier's path; with parameters it is the path and the parameters sorted by name, `carrier[name=value,name=value]`. Which instances a Plan requires, and why, is the using system's decision: Testing never chooses them. A Plan written before Carriers could be collected collects none, and reads and runs exactly as it did. A Plan may collect no Suite yet. Testing owns only `suites`, `carriers` and the body: every other frontmatter key belongs to the using system, and Testing never reads it. Where a Plan lives, and who adds to it, is the using system's decision.

A **Suite** is a directory holding `suite.json`, an object whose `tests` states what the Suite tests. A `tests` relation, a Test Case's or a Suite's, claims that the Test Case or Suite that declares it is sufficient evidence for what it names. A Suite's `tests` has the form of a Test Case's: an object of kinds, each key a plain name and each value a non-empty list of distinct ids, strings without whitespace. It may name several, and several Suites may name the same one. It claims that the Suite as a whole is sufficient evidence for them, and it is declared by the Suite toward what already exists, never by what it names. Every Case file anywhere beneath the directory belongs to the Suite; there is no other membership, and the Cases are the evidence. When what a Suite claims is sufficient only through several Cases together, the Suite makes the claim and those Cases do not individually declare that same relation. A Suite with no Case is refused, since it protects nothing. A Suite may state no `tests`: a `suite.json` written before the relation holds a `concern`, prose that Testing still accepts and gives no meaning, so that Suite collects its Cases and claims nothing. Several Test Cases and Suites may each sufficiently test the same thing: the rule is about what each claim asserts, not about how many make it. `readSuite` in `scripts/testing.ts` reads a Suite's `tests` and refuses it when it is not that form. Which Cases protect an id is still computed from Test Cases only: `testCasesTesting` and what is derived from it do not yet read a Suite's `tests`.

A **Case** is one file named `*.test.js` or `*.test.ts`, or a module variant of either (`.mjs`, `.cjs`, `.mts`, `.cts`), whose tests use Node's test runner, `node:test`. Its tests state the claims it makes. A Case passes only when executing it succeeds and every test it reports ran and passed: a Case that ran no test, or skipped one, proves nothing.

A Case file is also a **Carrier** of traceable **Test Cases**. A Test Case opts into traceability by one explicit source declaration: a top-level statement of the Carrier that calls the local name of its value default import of `node:test` with exactly three arguments, none spread, a non-empty string literal name, an object literal holding a plain `tests` property, and anything as the third: `import test from "node:test"; test("works offline", { tests: { requirement: ["works-offline"] } }, () => {});`. Its identity is the Carrier's path and that name, written as the one-line JSON array of the two. `tests` is a literal object of kinds, each key a plain name and each value a non-empty list of distinct string-literal ids without whitespace; a Test Case may declare any number of references, and any number of Test Cases may declare the same one. It is refused when it is not that literal, when `tests` is stated twice in one options object, or when two declarations claim one name, since the identity is then ambiguous. The declaration is read from the Carrier's syntax, parsed with `@babel/parser`, never by executing it: text in strings and comments is nothing. It states trace meaning: this Test Case tests these things, and claims that it alone is sufficient evidence for them. It does not state that Node registered or ran the call, which a Run shows. Everything else, every other use of `node:test` and every other call or property, is ordinary syntax outside this capability: neither read nor refused. The reference belongs to its declarer alone: what it names is never changed to learn of it, a Plan states none, no declaration names a Test Case, and there is no index to keep. Testing knows no kinds and does not check that an id names anything; the using system decides which kinds it accepts and whether the meaning exists. A Test Case tests only what it names: no relation of the named meaning, such as one that replaces it, is followed. `readTestCases` and `parseTestCases` in `scripts/test-cases.ts` read the Test Cases of a Carrier, and `testCasesTesting` computes, from the Test Cases given, which of them test a kind and id. For TypeScript, `scripts/tests-option.d.ts` declares `tests` as an option of `node:test`: it is this skill's metadata, not something Node defines. Traceability is of the Test Case, while a Suite still collects Carriers and a Run still executes and reports them, a Case above being the Carrier.

A Test Case can supersede an earlier one, so its HOW moves on while the earlier one stays exactly as it was written. A Test Case may add one plain `supersedes` property beside `tests` in the same options object, a literal list of exactly two string literals, the carrier and the name that identify the earlier Test Case: `test("how now", { tests: { requirement: ["works-offline"] }, supersedes: ["old.test.ts", "how then"] }, () => {});`. It is refused when it is not that literal or is stated twice. The relation belongs to the newer Test Case alone, like a reference to meaning: the earlier one names nothing and is never touched, and the relation is computed from the Test Cases, never stored. Supersession records HOW history. It does not delete, invalidate or unrun the earlier Test Case, which stays addressable and runnable historical HOW, and it does not by itself make it inactive: whether a Test Case still protects something is decided per `tests` edge. A Test Case is active for a kind and id it tests unless a later Test Case of its own lineage, the line of Test Cases that supersede it one after another, tests that same kind and id too. So when TC₁ tests R1 and R2 and TC₂ supersedes TC₁ and tests R1, TC₂ is active for R1 and TC₁ remains active for R2, the only protection it has; a superseding Test Case need not test everything its predecessor tested. Activity is computed from the supersession graph and the `tests` edges of the Test Cases being considered, never from a stored flag, dates, history, ordering or where a Test Case lives, so the same Test Case can be active in some material and not in other. Testing refuses a lineage whose target names no Test Case among those it is given, that supersedes itself or is a circle, or that has a Test Case immediately superseded by more than one, since which is later would be ambiguous: it reads declared meaning only and never judges whether two Test Cases prove the same thing. `readSupersession` in `scripts/supersession.ts` returns each superseded Test Case's superseder with those errors, and `currentTestCasesTesting` the Test Cases, among those given, that are active for a kind and id. Supersession is of Test Cases, while a Suite still collects Carriers and a Run still executes them all: a Carrier may hold Test Cases beyond the ones it declares, so a superseded Test Case does not make its Carrier obsolete. `carriersCurrentlyTesting` in `scripts/supersession.ts` answers which Carriers hold the Test Cases active for any of the kinds and ids given: a Carrier is selected by its active Test Cases alone, so one holding a Test Case superseded for one id but active for another is selected, and one with no active Test Case for any is not. The Carriers are paths, each once and sorted; they are computed from the Test Cases given, never stored, in a single pass, and a refused lineage answers its errors instead. `testCasesProtecting` in `scripts/supersession.ts` answers the Test Cases themselves: each Test Case active for any of the kinds and ids given, once however many of them select it, with the ids that select it, sorted, in the same single pass and with the same refusal. Testing defines no Test Data: an entry names the ids that selected its Test Case so that whatever is relevant to executing it for them has something to be keyed by, and nothing more is decided here. The answer is computed, never stored, and a Plan is as much authored and stored as it ever was; whether a using system derives a Plan from it is its decision. Which ids are protected, and what Plan is written of the Carriers, is for the using system: a Suite still collects whole Carriers, a Plan may collect Carriers one by one, and a Run still executes every Carrier it collects.

A **Strategy** is the using system's lasting decisions about how it uses Testing: where Suites and Plans live and who owns them, which Plan is run, where and when, and how one Plan follows another. Testing reads no Strategy and interprets none of it; it executes only the Plan it is given.

Run a Plan with `scripts/run.ts <plan> [candidate]`. The testing root, which the Plan and its Suites are read from, is the current directory; the candidate, the state being tested, defaults to it. These are often the same state, but they are two roles: each Case is executed in its own process, with the candidate as its working directory, under the same Node and loaders (`--import`, `--require`, `--loader`) `run.ts` runs under, whether given on its command line or in `NODE_OPTIONS`, and none of its other options (with `tsx`, TypeScript Cases run as they are). A loader named by a relative path is resolved from where `run.ts` runs, so it names the same file in the candidate. Node's test runner reports each Case to a file of its own, apart from anything the Case prints, so only that report decides the Case. A Case reaches what it tests through its working directory, never through its own location, so the same Case can judge a candidate it was not written beside. Nothing checks that it does.

A broken Plan or Suite is refused before any Case runs. Otherwise the Run is printed: the Plan, the candidate, the conditions (Node version, platform, architecture), one `pass` or `fail` line per instance it performed with the output of every Case that did not pass, one `unrun` line per instance it left unrun, and finally what it showed: `holds`, `does not hold` or `incomplete`. The conditions are what the Run observed of where it executes, each a name and a string. A Run provides the parameters its conditions state: it performs an instance only when every parameter of it is one of its conditions with that very value, and leaves the rest unrun. A name the Run does not state is never provided, so an instance is never evidence under conditions nothing observed, and Testing knows no name and no value beyond their equality. A parameter is not Test Data: nothing is passed to the Case, which is executed as it is, and what a parameter says is under what conditions that instance counts. A Run reports only what it performed. The Plan holds by a Run only if every instance it requires, through its Suites or directly, was performed and passed. It does not hold if an instance that was performed did not pass, which is so under any conditions. `incomplete` is neither: nothing that was performed failed, but an instance is under parameters these conditions do not provide, so the Run does not show the Plan and does not show that it fails. An unrun instance is not a skip, which proves nothing and keeps a Case from passing. `run.ts` fails unless the Plan holds: it exits 0 only then, 1 when it does not hold, and 3 when the Run is incomplete. A Plan that states no parameters has only instances under none, and a Run of it is exactly what it was. From code, `runPlan` in `scripts/testing.ts` returns the Run, observed under the conditions of its own process, and `readPlan`, `readSuite` and `readPlanSuites` return the same errors. `runPlanUnder` runs under conditions it is told, so that a using system can test what several Runs show; Testing cannot tell that they are true, so only `runPlan` observes.

Holding is what one Run shows of a Plan. A Plan that requires instances under different parameters is **evidenced** by Runs whose conditions provide each of them: every instance it requires passed in at least one of the Runs and failed in none. A Run that left an instance unrun neither supports it nor counts against it, and one Run that left none unrun is evidenced exactly when it holds. `planEvidence` in `scripts/testing.ts` computes it in one pass from the outcomes of the Runs, `outcomes` of a Run or `readReport` of the report `run.ts` printed, and `scripts/evidence.ts <report>...` prints `pass`, `fail` or `unevidenced` per instance, then `evidenced` or `not evidenced`, and exits 0 only when evidenced. Reports that do not require the same instances are not Runs of one Plan, and are refused. Which Runs are offered is the using system's decision, as is that they judged the same candidate and were made where they say: Testing keeps no Run and nothing here can check either, as nothing checks it of one Run.

Testing also computes **Regression**: the protection that must keep holding after a Change. Protection is stated as opaque identities: a non-empty string without leading or trailing whitespace, compared by exact equality, which Testing never interprets, normalizes or resolves. What an identity points to, and whether it points to a Suite, a Case or anything else, is the using system's decision. A Change's **Feature** adds protection identities; its **Acceptance** explicitly gives up identities that were protected before it. Regression is computed, never stated, so it is never weakened by omission: an identity the next Change leaves out stays protected. Each is a set, and the order of identities carries no meaning. The first Regression is the Feature, `R₀ = F₀`, and each next one follows from the one before it, `Rₙ = Rₙ₋₁ − Aₙ + Fₙ`. A transition is refused, and nothing is computed, if it accepts an identity the previous Regression does not protect (so the first Change cannot accept any), introduces one it already protects, introduces and accepts the same identity, or holds a malformed or repeated identity. An identity given up earlier may be introduced again when the previous Regression handed to the computation lacks it; anything stronger needs history, which Testing never reads. The computation depends only on the three sets it is given, not on Git, GitHub, repository history or how Changes were ordered, and the same sets always give the same result; `computeRegression` in `scripts/regression.ts` returns the Regression sorted, a fixed representation with no meaning, or the errors. Another resolver may replace it without changing these meanings. Testing does not keep Regression, or decide where Feature and Acceptance are stated.

Authorise was earlier called Acceptance, and earlier material that says Acceptance means Authorise: the computation takes the set only as `authorise` and refuses an `acceptance` it is handed rather than guess, so a set is never silently dropped under the retired name. Testing keeps no record of a Run: the Run is observed where it is executed. It does not bound a stuck Case, isolate a Case from the machine it runs on, or prove that the Plan, Suites and Cases it reads are the ones that were accepted; those belong to the using system. A Plan only collects: it cannot remove, replace or relate one Case to another, and Testing never judges whether two Cases prove the same thing.
