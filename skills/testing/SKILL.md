# Testing

A test proves a claim about what the tested thing does, and can be run again to prove it again.

State the claim. A test case is one claim about behaviour its user relies on, stated as a sentence that is true when the test passes, together with the proof of that claim. The claim, not its inputs, makes the case: more evidence for the same claim belongs to that case, and a new claim is a new case. State what is promised, not how it is done today, so the case outlives a change of mechanism. The claim says nothing about where or how the case is run.

Prove all of it. The proof covers exactly what the claim says: an exact result where the claim is exact, every entry where it speaks of a whole, everywhere a second one could be where it says there is only one. A case that would still pass with its claim broken proves nothing, so check that breaking the promise makes it fail. A failing case then names the claim that broke.

Keep test data apart from test cases. Test data is what a case proves its claim over: the inputs it is given, the conditions it is put in, such as which step fails, and the results it must produce. Its role makes it data, not its form: a file, a directory tree, a named row in a table, or a description of state that can only be built while the test runs. Name each item for what it shows. More data is more evidence for a claim, not another case, and the data a claim needs depends on its subject: the same claim about two subjects may need different data to cover all of it. What the claim itself says, such as the error it promises, belongs to the case. What only makes the test possible, such as the scratch place it works in, how a condition is produced or the platform it runs on, is not test data. Keeping data apart from the case lets the claim be read without its data in the way, and lets the same data serve several claims. Where test data is kept and how it is organised is the using system's decision.

Know which case it is. A case is its claim about its subject. The subject is what the claim is about, such as a function, a capability, a state a system keeps, or what a system produces; the platform, the runtime and the directory a case is run from belong to the run's environment, not to its subject. Give a case its subject rather than let it take whatever surrounds it when it runs: a case that reads the state around it has its subject chosen by where it happens to run, can judge something other than what it claims to, and finds nothing wrong with a subject that is not there, so make a missing subject fail the case. Where a case is kept and what it is called are its address: they find it among the cases of one version, and are not what it is. The same claim about the same subject is the same case wherever it is kept, whatever it is called and however it is proven; another claim, or the same claim about another subject, is another case, even at the same address. A case states its own relations beside it, such as the commitments it helps prove and the failures it reproduces, so they move and are renamed with it, and nothing finds them by its address. Whoever keeps a case owns it and decides what it may point at: an owner keeps cases about its own subjects, and where a relation must reach something the owner may not depend on, it needs a case kept by someone who may, about their own subject, which is another case. Read cases one way: whatever finds cases for one purpose, such as which commitments they prove or which to run, finds them as every other does, so what counts as a case, and that a case named but never run is none, is decided once.

Refactor cases, and keep what they prove. Testing learns by refactoring its cases, not only by adding them: cases found to make one claim over different data become one case with that data; a case found to make several claims becomes one case for each; a case that takes its subject from where it runs is given it; setup several cases repeat is drawn out of them. A refactoring keeps each claim and its subject, and with them every relation, which travels with the case. It must not weaken what is proven: the refactored proof must still fail wherever the old one failed with the claim broken, and every item of data the old cases proved the claim over stays evidence, so show both, as for any case. A change that narrows or broadens a claim, or turns it to another subject, is not a refactoring: it retires the old case and makes a new one, and each relation is decided again for the new claim rather than carried over. Changing only which commitments a case says it helps prove leaves the case as it is but changes what those commitments are shown by: judge it as a change to the commitments, which may be shown less strongly than before.

Know what cases promise together. A test suite is a commitment that its cases prove together, whether one case or many: a promise stated once, in the words of whoever makes it, such as that creating something is all or nothing. The commitment, not its members, makes the suite: its cases can be split, merged, replaced or moved to another owner while the commitment stays, and one case may help prove more than one commitment. A suite may draw on cases owned by different parts of a system; its meaning lives with whoever makes the promise, while its cases stay with what they test. A file of tests, the set a runner happens to execute, or cases that make the same claim about different subjects are not a suite by themselves. Let each case say which commitments it helps prove, naming each by the place where it is stated, so a commitment's cases can be found without the commitment listing them. Changing how a case proves its claim leaves its suites as they are; changing what a case claims means checking every commitment it helps prove.

Make it repeatable. Run again against the same version in the same environment, a test gives the same result: it does not depend on the order tests run in, on which other tests run with it, or on anything an earlier run left behind.

Know what a run proved. A test run is one occurrence of executing something testing can run, such as a case, against one version of what it tests in one environment, together with what it observed for each case it reached: passed, failed, or not run. What else a run may execute besides cases is not settled here. Cases and their data outlive every run, and no run changes them; keeping a record of a run is not what makes it one. A run's result holds only for what it exercised: the cases it actually ran, in the version it ran them in, the version of what they test it ran them against, and the environment it ran in, such as the platform, the runtime or how files were checked out, wherever these can change the result. A case skipped in a run proved nothing in it. The version a run exercises need not be the one its cases were written for: running a case against a version that breaks its claim is how the case is shown to be able to fail. What a run executes, and where, is decided outside the run.

Plan what must be shown. A test plan states intended testing: which subjects must be demonstrated, under which conditions, and for what, such as what a change must prove before it is accepted. It exists before any run carries it out, and one plan may be carried out by several runs, one for each condition it names. A plan names the commitments, the suites, it must demonstrate, never cases directly: cases are reached through the suites they help prove, so cases and their proof can change beneath a plan without changing it, and a plan and a suite relate many to many as suites and cases do. Say for each commitment what shows it: its cases, another check such as one of stored results, or both. A commitment the plan says its cases show must have at least one case pointing at it; one shown only by another check needs none, but the plan names that check, so a commitment without cases is a decision the plan states, never an oversight. How a run finds the cases, such as a file pattern, is execution mechanics, not part of the plan. The plan decides the conditions a result must hold for, such as platforms and runtimes, and which versions of the checks judge a change: the change's own checks can prove what it adds, but checks the change can alter cannot protect an existing commitment against it. Give a plan one place and one identity, so a run can say which plan it carried out, in which version, and a change to the plan is seen for what it is, a change to what testing promises. Where something enforces the plan, it follows the plan rather than stating it.

Keep what was promised. A regression plan is a test plan whose purpose is that what is already promised stays true as changes are accepted: it names the commitments that must keep holding, and a change is accepted only once they are shown again for it. Because it protects what already exists, it needs checks the change cannot alter as well as the change's own: the accepted version's cases, chosen by the accepted version's own account of which commitments each proves, run against the change. The change's cases then prove what it adds and what replaces a commitment, and where a commitment has only the change's own checks, the plan says so. A using system's regression plan says which commitments, conditions and checks are its own, and points back here for what a regression plan is.

Decide what testing preserves. A test strategy is the lasting set of decisions every plan follows: what testing must preserve, what a change must prove, and how what one change proves becomes what later changes must preserve. It outlives its plans and shapes many of them: a regression plan for what is already accepted, and a plan for each change in progress, which must show that the regression still holds, apart from the commitments it names as replaced or withdrawn, and prove what the change adds. The same cases and suites can serve both. When a change is accepted, the commitments its plan proved, under the conditions it proved them, join the regression the next change must keep. Commitments the change leaves in place are judged by checks it cannot alter, and where no such check exists yet, the plan names the gap; a commitment the change replaces or withdraws is named in its plan, because the checks that protected it would otherwise reject the change. A replaced commitment's successor commitment is proven by the change's own checks; a withdrawn one simply leaves the regression, visibly, when the change is accepted. So that a change can say which commitments it retains, replaces or withdraws, state each commitment where its statement does not change in place, and let later statements supersede it, leaving it as it was: a replacement states the commitment made in its place, and a withdrawal states that the commitment is no longer made, and why, succeeding the old statement without making a commitment of its own. A commitment stated where it can be edited in place changes whenever its statement does.

Decide how testing learns. The strategy also says how coverage is chosen, such as proving a claim in every environment the tested thing supports wherever the environment can change the result, and saying where it is not proven. It says how failures are learned from: a failure found by review or use gets proof that fails before the fix and passes after it, wherever it was missing: a new case for a claim not yet stated, new data for a claim already stated, a proof that covers more of its claim, or a condition the plan did not yet name. When the same kind of failure keeps being found, the fix changes the mechanism that lets it happen instead of only the instance found, while that proof still covers the instance.

Anchor the testing. A using system's testing has one anchor: a directory, `test/` by default, where agents working with tests enter. Create it with `scripts/create-anchor.ts [dir]`. It creates `<dir>/AGENTS.md`, which routes agents working with tests to this skill, and nothing else, and refuses when `<dir>` already exists. The anchor is an entry point, not a container: tests and their data stay wherever the using system keeps them.

What to test, and where and when to run it, are the using system's decisions, stated in its strategy and plans; which cases to keep follows from the commitments they help prove. This skill says how a test is written and creates the anchor.
