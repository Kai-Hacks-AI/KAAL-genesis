# Testing

A test proves a claim about what the tested thing does, and can be run again to prove it again.

State the claim. A test case is one claim about behaviour its user relies on, stated as a sentence that is true when the test passes, together with the proof of that claim. The claim, not its inputs, makes the case: more evidence for the same claim belongs to that case, and a new claim is a new case. State what is promised, not how it is done today, so the case outlives a change of mechanism. The claim says nothing about where or how the case is run.

Prove all of it. The proof covers exactly what the claim says: an exact result where the claim is exact, every entry where it speaks of a whole, everywhere a second one could be where it says there is only one. A case that would still pass with its claim broken proves nothing, so check that breaking the promise makes it fail. A failing case then names the claim that broke.

Keep test data apart from test cases. Test data is what a case proves its claim over: the inputs it is given, the conditions it is put in, such as which step fails, and the results it must produce. Its role makes it data, not its form: a file, a directory tree, a named row in a table, or a description of state that can only be built while the test runs. Name each item for what it shows. More data is more evidence for a claim, not another case, and the data a claim needs depends on its subject: the same claim about two subjects may need different data to cover all of it. What the claim itself says, such as the error it promises, belongs to the case. What only makes the test possible, such as the scratch place it works in, how a condition is produced or the platform it runs on, is not test data. Keeping data apart from the case lets the claim be read without its data in the way, and lets the same data serve several claims. Data is always used by a case, but need not be provided by it: a suite may provide data its cases share, and a plan data the testing it requires needs; whichever provides it, the case is what knows how to use it to exercise its claim. Where test data is kept and how it is organised is the using system's decision.

Know which case it is. A case is its claim about its subject. The subject is what the claim is about, such as a function, a capability, a state a system keeps, or what a system produces; the platform, the runtime and the directory a case is run from belong to the run's environment, not to its subject. Give a case its subject rather than let it take whatever surrounds it when it runs: a case that reads the state around it has its subject chosen by where it happens to run, can judge something other than what it claims to, and finds nothing wrong with a subject that is not there, so make a missing subject fail the case. Where a case is kept and what it is called are its address: they find it among the cases of one version, and are not what it is. Its title states its claim for whoever reads it, but the claim is what the case asserts about its subject, which a clearer title leaves as it was. The same claim about the same subject is the same case wherever it is kept, whatever it is called and however it is proven; another claim, or the same claim about another subject, is another case, even at the same address. A case states its own relations beside it, such as the commitments it helps prove, the suites it belongs to and the failures it reproduces, so they move and are renamed with it, and nothing finds them by its address. Whoever keeps a case owns it and decides what it may point at: an owner keeps cases about its own subjects, and where a relation must reach something the owner may not depend on, it needs a case kept by someone who may, about their own subject, which is another case. Read cases one way: whatever finds cases for one purpose, such as which commitments they prove or which to run, finds them as every other does, so what counts as a case, and that a case named but never run is none, is decided once.

Refactor cases, and keep what they prove. Testing learns by refactoring its cases, not only by adding them: cases found to make one claim over different data become one case with that data; a case found to make several claims becomes one case for each; a case that takes its subject from where it runs is given it; setup several cases repeat is drawn out of them. A refactoring keeps each claim and its subject, and with them every relation, which travels with the case. It must not weaken what is proven: the refactored proof must still fail wherever the old one failed with the claim broken, and every item of data the old cases proved the claim over stays evidence, so show both, as for any case. A change that narrows or broadens a claim, or turns it to another subject, is not a refactoring: it retires the old case and makes a new one, and each relation is decided again for the new claim rather than carried over. Changing only a case's relations, such as which commitments it says it helps prove or which suites it belongs to, is not a refactoring of the case either: judge it as a change to those relations and to what the commitments and suites they reach are shown by, not as a change the case's identity settles.

Compose cases into suites. A test suite groups cases around a shared testing concern, such as that a capability works without a network. It does not know how that concern is tested: only its cases do, each stating one claim about its subject and proving it. The concern, not its current cases, gives a suite its meaning: cases join and leave it as understanding of how to test the concern improves, and it stays the same suite. A suite is stated once, in a place of its own that says what concern it serves; that place is its identity, and no plan owns it, so any plan needing that testing can name the suite rather than list its cases, and a run can say that it ran it. Each case says which suites it belongs to, beside it, naming each by the place where it is stated: a suite never lists its cases, a case's memberships move and are renamed with it, and a case may belong to several suites without being kept twice. A suite is not a commitment: a commitment is a promise that testing demonstrates, a suite a concern that testing is grouped around. Let each case say which commitments it helps prove apart from which suites it belongs to, naming each commitment by the place where it is stated, so a commitment's cases can be found without the commitment listing them. The two often align, and a suite may group exactly the cases of one commitment, but a suite's cases may help prove several commitments, one commitment may be shown by cases of several suites, and either can change while the other stays. A suite groups cases, not examples of one: more data for a claim is more evidence for its case, not another case of the suite, and cases that use the same data are not a suite for using it. A file of tests, the set a runner happens to execute, or cases that make the same claim about different subjects are not a suite by themselves either. The conditions testing must hold under are not the suite's: the plan that names it says under which conditions it must be shown, and each run records the conditions it had; a condition the concern itself needs, such as having no network, is forced by its cases. A case names only suites its owner may depend on: where testing of a part that may not depend on a suite belongs to it, a case kept by someone who may, about their own subject, is what joins it. A run of a suite reaches every case that belongs to it in the testing state the run records, and no other, and observes each as any run does; whether what it observed is enough is for the plan that named the suite to say. Structure is not evidence: a suite can be stated before any case of it is known, since testing is often planned outside in, a plan's purpose before its concerns and a concern before the claims that prove it, and a suite no case belongs to yet stands for a concern no case supplies proof for. A run of it reaches nothing and observes nothing, which is no evidence, never success, and leaves its concern undemonstrated. Nor can structure show that a suite holds every case its concern needs, any more than that a case holds every item of data its claim needs: review, failures and what runs teach show what is missing, and a suite's cases grow as they do. Refactoring cases keeps their memberships, as it keeps every relation: a case moved or retitled stays in its suites, and cases merged into one case over their data stay in every suite they belonged to; a case split into several claims has each new case's suites decided again. Changing how a case proves its claim leaves its suites and commitments as they are; changing what a case claims means checking every suite it belongs to and every commitment it helps prove.

Make it repeatable. Run again from the same testing state, against the same tested state, under the same conditions, a case is observed the same: it does not depend on the order cases run in, on which other cases run with it, or on anything an earlier run left behind. Where it is observed differently, a condition that changes it is not yet recorded, or the case is not repeatable: find the condition, record it, and where the case can force it, force it, so every run observes it.

Know what a run proved. A test run is one occurrence of executing something testing can run, a case, a suite or a plan, against what it tests, under the conditions it was executed in, together with what the execution reached and what it observed there. What is run comes from a testing state, which also supplies the cases it reaches and their test data; what they test is the tested state. They are often one state, such as a version's own testing run against it, but need not be: an accepted version's cases run against a proposed change is a run whose testing state and tested state differ, and saying which is which is part of saying what it proved. A run hands each case it reaches its subject from the tested state, rather than leaving the case to take whatever it happens to be kept or run in. A run observes each case what it runs was to reach as passed, when it ran and its claim held; failed, when it ran and its claim did not hold; or not run, when it was not exercised, as a skipped case was not: a case not run proved nothing, and is never counted as passed. A run names each case by its address in the testing state it records, so it needs no identity for a case beyond that state; whatever its executor reports that none of those cases accounts for observes none of them, and is kept apart. The conditions a run records are those that can change what it observes, such as the platform, the runtime or how files were checked out, not everything about where it happened: the same testing run on two platforms is two runs. A case that passed in a run proves only that its claim held for that tested state, using that testing state, under those conditions. Keeping a record of a run is not what makes it one, and a run need not be kept until something reads its record. The tool that executed it, and the job, process or log that carried it out, are not the run: they execute, carry or keep runs. A run of a suite or a plan reaches cases; whether what a run observed is enough, such as whether a commitment was demonstrated, is not the run's to say. The version a run exercises need not be the one its cases were written for: running a case against a tested state that breaks its claim is how it is shown able to fail, and running a refactored case against the tested states that broke the cases it replaces, which must fail it too, is how it is shown to prove at least as much. What a run executes, and where, is decided outside the run.

Plan what must be shown. A test plan states a testing purpose: why testing is carried out, such as that what is already promised stays true, or what a change must prove before it is accepted, and so what must be shown, and under which conditions. It does not know how any claim is tested; its cases do. Its purpose, not what currently carries it out, gives a plan its meaning: give it one place and one identity, so a run can say which plan it carried out, in which version, and a change to the plan is seen for what it is, a change to what testing promises. What carries a plan out is stated beneath it, not in it: let each suite say which plans it serves, as each case says which suites it belongs to, so a plan never lists its suites or its cases, can be stated before any suite serves it, and keeps its purpose while the concerns that carry it are found, refined, split or replaced; one suite may serve several plans. A plan may also name what it must demonstrate directly, such as commitments, reached through the cases that say they help prove them, and proof other than cases, such as a check of stored results. Say for each commitment what shows it: its cases, another check, or both. A commitment the plan says its cases show must have at least one case pointing at it; one shown only by another check needs none, but the plan names that check, so a commitment without cases is a decision the plan states, never an oversight. The plan states the sets of conditions its testing must be shown under, such as each platform and runtime it supports, and may require a proof under fewer; a suite and its cases stay the same under every set. A plan may provide test data its testing receives, as a suite or a case may: it does not know how its cases use that data, and data it provides is neither a case's identity nor a suite's membership. How a run finds the cases, such as a file pattern, is execution mechanics, not part of the plan. A run of a plan reaches only what the plan requires: the cases of the suites that serve it and those that say they help prove what it names, each once however many requirements reach it, and the proof it names, and it records what it observed of each requirement; testing the plan does not require is not reached, so not everything needs running every time. A run has one set of conditions, so a plan required under several is carried out by several runs, each of the plan under one set. Whether a plan's purpose was demonstrated is the plan's to judge, from its runs, declaratively: under each set of conditions it is required under, a requirement failed if a run observed it fail or kept something apart, held if a run reached it and every case it reached passed, and is otherwise not demonstrated, as when no run had those conditions, a suite no case belongs to reached nothing, or what was reached was not run. A plan is demonstrated only when every requirement held under every set, and a plan that requires nothing yet demonstrates nothing. The plan decides which versions of the checks judge a change: the change's own checks can prove what it adds, but checks the change can alter cannot protect an existing commitment against it. Where something enforces the plan, it follows the plan rather than stating it.

Keep what was promised. A regression plan is a test plan whose purpose is that what is already promised stays true as changes are accepted: it names the commitments that must keep holding, and a change is accepted only once they are shown again for it. Because it protects what already exists, it needs checks the change cannot alter as well as the change's own: the accepted version's cases, chosen by the accepted version's own account of which commitments each proves, run against the change. The change's cases then prove what it adds and what replaces a commitment, and where a commitment has only the change's own checks, the plan says so. A using system's regression plan says which commitments, conditions and checks are its own, and points back here for what a regression plan is.

Decide what testing preserves. A test strategy is the lasting set of decisions every plan follows: what testing must preserve, what a change must prove, and how what one change proves becomes what later changes must preserve. It outlives its plans and shapes many of them: a regression plan for what is already accepted, and a plan for each change in progress, which must show that the regression still holds, apart from the commitments it names as replaced or withdrawn, and prove what the change adds. The same cases and suites can serve both. When a change is accepted, the commitments its plan proved, under the conditions it proved them, join the regression the next change must keep. Commitments the change leaves in place are judged by checks it cannot alter, and where no such check exists yet, the plan names the gap; a commitment the change replaces or withdraws is named in its plan, because the checks that protected it would otherwise reject the change. A replaced commitment's successor commitment is proven by the change's own checks; a withdrawn one simply leaves the regression, visibly, when the change is accepted. So that a change can say which commitments it retains, replaces or withdraws, state each commitment where its statement does not change in place, and let later statements supersede it, leaving it as it was: a replacement states the commitment made in its place, and a withdrawal states that the commitment is no longer made, and why, succeeding the old statement without making a commitment of its own. A commitment stated where it can be edited in place changes whenever its statement does.

Decide how testing learns. The strategy also says how coverage is chosen, such as proving a claim in every environment the tested thing supports wherever the environment can change the result, and saying where it is not proven. It says how failures are learned from: a failure found by review or use gets proof that fails before the fix and passes after it, wherever it was missing: a new case for a claim not yet stated, new data for a claim already stated, a proof that covers more of its claim, or a condition the plan did not yet name. When the same kind of failure keeps being found, the fix changes the mechanism that lets it happen instead of only the instance found, while that proof still covers the instance.

Anchor the testing. A using system's testing has one anchor: a directory, `test/` by default, where agents working with tests enter. Create it with `scripts/create-anchor.ts [dir]`. It creates `<dir>/AGENTS.md`, which routes agents working with tests to this skill, and nothing else, and refuses when `<dir>` already exists. The anchor is an entry point, not a container: tests and their data stay wherever the using system keeps them.

What to test, and where and when to run it, are the using system's decisions, stated in its strategy and plans; which cases to keep follows from the commitments they help prove. This skill says how a test is written, creates the anchor, and turns what executed a run's cases reported into what the run observed: `observe` in `scripts/observe.ts` takes the cases a testing state holds, by address, and the executor's reports, and returns one observation for each case, in their order, as passed, failed or not run, a skipped case or one without a report being not run, together with the reports no case accounts for, matched one to one so two cases at one address need two reports; and `reached` in `scripts/suite.ts` takes those observations and which suites each case says it belongs to, and returns what a run of one suite observed: the observation of every case that belongs to it, and of no other, none for a suite no case belongs to yet; and `evidence` in `scripts/plan.ts` takes what a plan requires, each under the sets of conditions it must be shown under, and what runs of it observed of each, and says whether each held, failed or is not demonstrated under each set, and so whether the plan's purpose was demonstrated.
