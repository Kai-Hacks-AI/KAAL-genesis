# Coding

Coding changes an implementation so that a claim it is meant to satisfy holds. It begins with executable evidence that the claim does not hold, red, and ends when that evidence, run again, shows the claim holding through the implementation responsible for it, green, with everything that held before still holding. Take the shortest coherent path between the two: the smallest change that makes the responsible implementation genuinely satisfy the claim, not the smallest change that makes the evidence pass. Hardcoding what a case expects, special-casing the input it uses, or catching the failure it provokes are short, and not coherent.

The evidence is not yours to change. What a case claims, its subject, its data, what runs it and whether a run passed belong to whoever keeps the testing, and a run, not the coder, says green. Never make red green by deleting or skipping a case, weakening what it asserts, turning it to another subject, changing its data to avoid the failure, taking it out of what runs, or hiding the failure. Change the implementation. When the evidence itself looks wrong, say so as a finding of its own, apart from the change, rather than rewriting it on the way to green. What counts as implementation follows from the case's subject, not from the kind of file: where the subject is test machinery, a checker or a script, that is the implementation, and changing it is coding.

Start from red. Before changing anything, run the case that states the claim and see it fail for the reason the finding describes. Where no case states it, stating one is testing's work, not part of this change: hand it back to whoever keeps the testing, or, where that is you too, do it as testing, apart from the change, and resume coding only once that case runs and fails for the reported reason. A repair made without red cannot show what it repaired, and a reproducer failing for another reason shows nothing about this one. Work that is new rather than broken starts the same way, from a claim testing has stated so it can be run and seen failing; do not build ahead of any claim. Where the evidence cannot run before the change exists, still have it before calling the change done.

Find the responsible implementation. Follow the failure from where it shows to what decides it: the subject the case tests, the owner that states the behaviour, and the path from one to the other; where a failure appears is often downstream of where it is made. Before writing a mechanism, look for the one that already states this meaning, such as a reader, a validator or a rule a neighbour already uses, and repair or use that. Do not pass the failure by at the point where it surfaced: filtering output, correcting a wrong result afterwards, catching and ignoring an error, or adding a second reader beside the one that is wrong. Two readers of one meaning drift, and each disagreement between them is the next failure.

Repair the rule, not the instance. A finding names one input; the defect is the rule the implementation got wrong, and that rule fails every input it covers. Ask what makes the reported input wrong, name the class it belongs to, and repair the rule for the whole class: every kind of entry that is not what the code can read, every value that is not what an absent one defaults to, every path that reaches the check. Admit what is known to be good rather than exclude what has been seen to be bad, since a list of exclusions grows by one with every finding. Read structured input with what understands its structure, not with a pattern that resembles it. Check what is read before reading it, and let what is missing fail rather than pass as empty. Where several paths need one rule, such as a check and the work it guards, let each go through the one place that states it, so no path skips it. When the same kind of failure keeps being found, or a mechanism keeps needing exceptions, the rule is still wrong: change or remove the mechanism that lets it happen, keeping every instance found as evidence. Where the evidence covers only the instance, say what more of the class it should cover; extending it is testing's.

Show that the repair made it green. Run the evidence again and see red become green. Then undo the repair, or break the rule it states, and see the case fail again: a case that stays green without the repair was not made green by it. Check any assumption the repair rests on, about a tool, a runner or a platform, by running it rather than by reasoning about it. Run everything that already held: a repair that breaks another claim is not green.

Stay on the path. Change only what the claim needs, and leave behaviour it does not ask about as it was. Another failure or a better structure found on the way is not part of this change: keep it where the using system keeps observed failures or possibilities, and leave it. Once green, restructure only while the evidence stays green; a restructuring that changes what is promised is not one.

Surface pressure you cannot resolve. Sometimes the coherent repair cannot be made where the responsibility lives: the same fix must be repeated in several places, an owner cannot do it without reaching into another, two owners each state one meaning and neither can be made the other's reader, or the claim can only hold if a rule moves from where it is enforced to somewhere else. That is evidence that the responsibility may belong elsewhere. Say what the evidence shows and leave deciding where a responsibility belongs to whoever decides it. Tell such pressure from hardening: repairs that each make one owner handle its inputs more carefully leave its boundary where it was. Likewise, when the claim itself turns out ambiguous, contradictory or impossible as stated, say so rather than decide what it meant.

The change is done when the claim is green: the evidence that was red holds, fails again without the repair, and nothing that held before stopped holding. Coding keeps no record of its own: the claim, its evidence, the failures and possibilities met on the way and what was learned each already have a place, and the reasoning behind a repair belongs with the change that carries it.
