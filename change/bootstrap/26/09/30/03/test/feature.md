# Feature

This Change moves the requirement that Changes be sealed into `check-seals`, and leaves CI's sealing as the writer that meets it. `check-seals` requires every Change present in a pull request's head to be sealed, touched relative to its base or not, so the same head has the same sealing verdict whatever its base or draft state. A ready pull request into a `kaal/*` flight or main whose head holds an unsealed Change is red; a draft, or a pull request against a base that is no admission, is held, its status pending, and is never reported as sealed. Where CI can write back, `seal-pull-request` seals exactly the Changes the pull request touches with the existing Change Sealing and `check-seals` turns green on the sealed head; elsewhere the Changes must arrive sealed. A flight into main may be held while its head contains an unsealed Change it did not touch, until that Change is sealed: a temporary hold is accepted over a verdict a change of base could make stale. The separate `seal-change` status is gone: there is one verdict, `check-seals`, and the writer publishes none. The sealing workflows are renamed `seal-pull-request` and `request-sealing`.

It composes; it does not seal. The rule is `gateOutcome` in `scripts/pull-request-sealing.ts`, run by `check-seals` from the trusted checkout over the head, the merge's second parent, which the run verifies is the status SHA; what sealing means and the bytes it writes remain `scripts/change-seals.ts`, and whether a seal is valid, not only present, remains the existing verification's over the merge.
