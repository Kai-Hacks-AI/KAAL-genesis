---
idea: KAAL could be assembled from independently birthable capability packages,
  with Genesis composing a selected configuration of required dependencies and
  optional integrations and establishing that configuration's initial sealed
  Regression R0
---

This possibility extends `ideas/modular-kaal/idea.md` and leaves that record as it was. That Idea let package dependencies close the selected capability composition. Work since then suggests that not every composition between capabilities is a dependency, so the two relations may need to stay distinct.

The evidence is that KAAL's Skills have been born as independent capabilities: managing-ideas, managing-defects, managing-requirements, testing, architecting and coding. Each time, KAAL chose independent capability plus composition over one capability absorbing another. Coding depends on nothing of KAAL's and on no other skill. It needs only evidence that can be run and seen red or green, and KAAL composes it with testing around that evidence without making testing a dependency. Coding also surfaces architectural pressure without depending on architecting. A skill's case points at nothing outside its skill, and Ideas, Defects and Requirements keep different meanings instead of becoming one record system. Git and GitHub carry KAAL's states without owning their meaning. Together this suggests that a Skill stays independently meaningful unless evidence establishes a real dependency, and that composition is not dependency.

If that independence became distributable, a relation between capabilities might be either of two kinds. A required dependency is one where A cannot meaningfully operate without B, so selecting A requires B. An optional integration is one where A and B each stay meaningful alone and compose more richly when both are present. Testing and defect management are the clearest current example of an optional integration. A failing case is valid evidence without any defect record, and a defect does not become part of testing. When both are present, a case may point at the defect it tests, and because a defect records no state of its own, runs of those cases might one day help show whether it still fails. The hypothesis to keep with this is that composition must not destroy capability independence. Testing alone means that a failing case is failing evidence. With defect management, the same evidence can also relate to a durable defect, and testing should not mean something different just because a neighbour is installed.

Genesis today births KAAL. A future Genesis might instead birth a selected configuration. It could take the selected capability packages, resolve their legitimate required dependencies, activate the optional integrations available among them, birth each capability, compose, validate and seal the result, and establish that configuration's initial accepted Regression as its R0. R0 would then belong to a configuration rather than to every KAAL: a testing-only KAAL and a testing-with-defects KAAL need not make the same commitments. Brain itself might be one selectable capability. The current KAAL relies on BRAIN because durable learning is central to how it develops, but that does not make BRAIN required for every configuration.

This is separate from the lineage of the KAAL being built when this was recorded. There, Genesis and the released `main` were conceptually R0, and `kaal/testing`, once demonstrated, sealed and released to `main`, was expected to become R1, as v0.0.2. That lineage is evidence for this Idea, not an instance of it. A Release was expected eventually to produce distributable package artifacts. If this Idea holds, a Release might produce independently distributable capability packages from the exact accepted and sealed source generation.

The first serious evidence is expected from finishing testing, preparing v0.0.2 and proving testing in a fresh repository. That work should show what testing actually needs to install, which of its relations are truly required and which are only optional, which KAAL-specific assumptions break its portability, what must be shared, what can stay inside testing, and what a Release actually needs to package. Brain and testing already reuse some common KAAL mechanics, so there may be a shared core, but that same work should show whether any of it deserves to be one. It could justify refining this Idea, birthing a packaging or composition capability, changing Genesis or extracting a core, or it could reject parts of this possibility. Shipping testing does not depend on any of this: the order is to learn what testing needs first, then design packaging and Genesis from the result.

This record keeps the possibility only. It does not commit KAAL to package boundaries, to one package per Skill, to npm or any other package technology, to what a core contains, to a schema for dependencies or optional integrations, to versioning or compatibility, to package discovery, or to a configuration format for Genesis. It does not change current Genesis, BRAIN, testing, FAR or Regression semantics, and it does not claim that modular KAAL exists.
