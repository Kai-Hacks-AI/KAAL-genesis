# Plan

A test plan states a testing purpose; what a plan is, is the testing skill's. This node records how KAAL states its plans, how they are carried out, and what stays particular to its Regression Plan.

KAAL states each plan in a file of its own, whose place is its identity: the Regression Plan in `test/regression-plan.md`, and any other in `plans/<name>.md`, named as portably as a suite. A plan's text states its purpose. A plan says how runs read what it requires in a `yaml` block under `## As runs read it`: the sets of conditions its testing must be shown under, as runs record them, where a version named is met by that version further qualified; the proof other than cases it requires, each under the sets it states for it or else under the plan's; and the test data it provides, a directory in the state. A plan without that section requires no conditions, no other proof, and provides no data.

What carries a plan out is stated beneath it, never in it. Each suite says which plans it serves with a `Serves: <place>` line, as each case says which suites it belongs to, so a plan lists neither its suites nor its cases: it can be stated before any suite serves it, one suite serves several plans, and the suites that carry a plan can be found, split or replaced while the plan stays as it is, byte for byte. A plan may also name commitments, whose cases are those that say they help prove them; a commitment is what a plan promises, not a concern that carries it, so a plan's commitments are never read as suites, nor its suites as commitments. The links check refuses a `Serves:` line that is not strictly written or names no plan the state states, a file in `plans/` that is not a plan's place, a plan whose requirements runs cannot read, or whose data is no directory inside the state, and a plan that says how runs read it but does not require, as proof, a check it names as showing a commitment.

KAAL runs a plan with `scripts/run.ts --plan <place> <testing-state> [tested-state]`. The run reaches only what the plan requires: the cases of the suites that serve it and of the commitments it names, each once, however many requirements reach it, executing only their files; it hands them the plan's data through `KAAL_PLAN_DATA`, which only the cases know how to use, so the same plan with other data can observe otherwise while nothing about any case or suite changes, and a run of a suite alone hands none. It records what it observed of each requirement. A run of cases does not reach proof other than cases: such proof, such as the seal checks, is shown by what carries it, and a run of a plan leaves it undemonstrated. A run has one set of conditions, so a plan required on Linux and Windows is carried out by at least one run on each.

Whether a plan's purpose was demonstrated is the plan's to judge, from its runs, and a run of a plan is printed beside that judgement: each requirement, under each set of conditions it is required under, held, failed or is not demonstrated, and the plan is demonstrated only when every requirement held under every set. A plan no suite serves yet, a suite no case belongs to, a case not run, a set of conditions no run had, and proof no run reached are no evidence, never success.

KAAL's Regression Plan requires its commitments, the suites that serve it, such as without Git, since its checks must need neither Git nor GitHub, and the seal checks on Linux, under the conditions it states. Its purpose, that what is accepted keeps holding, is still judged by the accepted regression's checker from the accepted regression's cases, as it was; a run of the plan shows what one state's own testing observes, and does not replace that judgement. The accepted regression does not protect which suites serve a plan: a suite that stops serving one is seen only by review.
