# Feature

A Feature is what a candidate newly promises relative to the accepted state it would succeed. KAAL's per-change testing is growing toward Feature, Acceptance and Regression: Feature establishes what the candidate newly promises and what must demonstrate it; Acceptance will decide which changes to inherited protection are deliberately accepted; Regression protects the accepted state that results. This node records only Feature.

A Feature cannot be read from the candidate alone. Every promise the candidate makes is in it, and most of them the accepted state already makes. So KAAL derives a Feature from the two states' files, as directories, and asks neither Git nor GitHub which is which: they only supply the states. A state states a commitment by naming its place in its Regression Plan, as every commitment of KAAL's is named, or by recording a Requirement, which is a commitment once recorded, before any plan names it. A commitment is identified by that place, as its cases point at it. The candidate's new promises are the places it states that the accepted state does not: `scripts/feature.ts` names them, and `requirements/new-promises/requirement.md` states that commitment. KAAL's first Requirements are this change's own new promises.

Requirements are where new promises belong. A commitment stated inside code, or in a `SKILL.md`, changes in place, so a promise added beside the old ones there has no place of its own, and no Feature can see it. A Requirement is a place of its own made only for its commitment, never rewritten, so its appearing is exactly a new promise. A Requirement rewritten in place is refused rather than read as kept or as new. A Requirement moved to another place is, by place, a new promise there, which asks for more evidence, never less.

A Feature depends only on what the two states state. It does not change with code, cases, suites or runs, so a refactoring that states nothing new has no new promises, and a Feature's meaning survives any rearrangement of the testing that shows it. Nor does it read what the accepted state states and the candidate does not: an omission is read as nothing at all, never as a promise given up. Feature has no way to say that something may be lost, and the accepted regression's own checks go on judging it as before. A replacement's successor is a new promise; that the old one may go is not Feature's to say.

KAAL's Feature Plan, `plans/feature.md`, is a plan like any other, and changes nothing about what a plan is. Its purpose is that what the candidate newly promises holds. It lists no promise, case or suite: whoever runs it derives the candidate's new promises and gives them to the run, and the plan requires each one as a commitment, shown by the candidate's own cases that say they help prove it, under the conditions it states, the Regression Plan's own. `requirements/new-promises-demonstrated/requirement.md` states that commitment. A new promise nothing proves is not demonstrated, since no run reached anything for it. A candidate that newly promises nothing gives the plan nothing to require: it requires nothing, and demonstrates nothing, which is all such a candidate owes. No suite serves the Feature Plan yet. One that did would be required of every candidate, whatever it newly promised.

What is left open is left for Acceptance or later. Feature does not see a new promise hidden in a statement that changes in place, nor a skill added under the one wildcard place of commitment 7. A commitment the accepted state records as a Requirement but never names in a plan is not new to a candidate that names it, so its Feature does not ask for its evidence; only the candidate's links then do. A candidate may change the Feature Plan's own conditions, and nothing but review protects them. States are named by where they are, so runs of one Feature on Linux and on Windows are not yet judged together, and nothing yet carries out the Feature Plan's runs on GitHub.
