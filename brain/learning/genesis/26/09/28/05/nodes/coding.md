# Coding

KAAL uses the **coding** skill so that turning a claim that does not hold into one that does, through the implementation responsible for it, is done by one discipline rather than rediscovered in each round of implementation and review.

KAAL had been doing this repeatedly without a capability for it, which is the evidence for moving it forward in BASS, from Bare to Skill. Most of what review found while KAAL's testing was built, from the trusted regression through the runnable Plan, the Feature Test Plan and Acceptance, was neither a wrong claim nor a misplaced owner but an implementation that did not yet do what was already meant, and the same mistakes recurred. A fix covered only the reported input, so the next round found its neighbour: links, then dangling links, loops, unreadable entries and pipes; `false`, then `null`, then `proof: null`; one npm hook, then the next. Line endings were normalised with one more exception per finding until the normalisation was removed. A second reader was written beside an owner that already stated the meaning, as Markdown sections, case titles and a state's entries each came to be read twice, until one reader remained. A place was read before it was checked, a check and a run applied one rule differently, output was filtered after the fact instead of the failure being prevented, and a value that was missing passed as empty. What repaired them recurred too: reproduce first, show the new case fails on the state before the fix and passes after it, repair the rule for its whole class, admit what is known good rather than exclude what was seen bad, reuse the owner that already states the meaning, and, where rules were rewritten, break them and see the cases fail. KAAL's defects show the same loop, in test machinery as much as elsewhere: a Windows race in checking a stuck init was reproduced by making the removal fail as Windows does, then repaired where the removal happens.

Coding is not testing. Testing owns the claim and its evidence: which cases exist, what they claim, their subjects and data, whether a run passed, and, as KAAL's test strategy says, that a failure found by review or use gets proof that fails before the fix and passes after it. Coding consumes that red and owns only the shortest coherent path to green; it never makes green by changing the evidence, and a run, not the coder, says green. Coding is not deciding where a responsibility lives either: when a repair cannot be made coherently where the responsibility sits, coding says so as evidence and leaves the decision to whatever decides it. Many findings that each harden one owner, as the Plan's did, are coding, not pressure on its boundary.

The skill depends on nothing of KAAL's and on no other skill: it needs only evidence that can be run and seen red or green, without Git or a repository host. KAAL composes it through BRAIN with testing, which states the claims and runs them, with managing-defects, where a failure worth keeping is recorded and a case that reproduces it points at it with `// Tests: defects/<name>`, and with managing-ideas, where a possibility met on the way is kept instead of being built into the change.

KAAL keeps no record of coding. What one would hold already has a place: the claim in its case or Requirement, the failure in a defect, a possibility in an Idea, what KAAL learned in BRAIN, and the reasoning behind a repair with the change that carries it. Nor does KAAL require coding of any change, or judge one by it.

The skill explains how to code. This node records why KAAL uses it.
