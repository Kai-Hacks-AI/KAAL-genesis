# Acceptance

Acceptance is what a candidate explicitly gives up of what the accepted regression protects. KAAL's per-change testing is growing toward Feature, Acceptance and Regression: Feature names what the candidate newly promises; Acceptance names, and only names, the inherited protection the candidate is allowed to lose; Regression will then be what was protected, less what was accepted, with what was newly promised and demonstrated. This node records only Acceptance.

Acceptance is about reduction, so it starts from what the accepted regression protects, never from a diff of files. What it protects is what the accepted Regression Plan requires, read as KAAL reads any plan's requirements: its commitments, the suites that serve it and its proof other than cases, each under the sets of conditions it is required under, as a plan's evidence judges runs; with what the plan says shows each commitment, such as the seal checks, and each file a wildcard commitment covers, such as each skill's `SKILL.md`. Acceptance owns no model of protection of its own beside the plan's requirements: the regression that follows reads the same requirements. A reduction is any of those the candidate's Regression Plan no longer requires: a requirement lost, one no longer required under a set of conditions, a check no longer said to show a commitment, a file a wildcard no longer covers, or a set of conditions nothing is required under any more. A stricter set, such as a later version of the same runtime, keeps what it implies. A candidate can remove, move or rewrite many files and reduce nothing, and a candidate can keep every file and still reduce, as by no longer requiring Windows. Cases are evidence for the requirements, not requirements, so moving, merging or rewriting them reduces nothing while what they show stays required. `scripts/acceptance.ts` derives the reductions from the two states' own files, as Feature derives new promises, and refuses what the links check refuses of either.

A reduction is accepted only by being named. A candidate names what it accepts losing in an acceptance record it adds to `acceptance/`, each entry naming a reduction, or the whole it is part of, such as all of a proof or a set of conditions wherever it is lost, and saying why. Silence retains: a reduction no entry names is refused, however obvious it seems, and so is an entry that names no reduction the candidate makes, so no waiver is kept in reserve. A record the accepted state already holds is history: it accepted a reduction of an earlier regression, accepts nothing more, and is never rewritten or removed, so a waiver can neither wait for a later loss nor be added again as if new. With no record, the candidate accepts nothing, which is right exactly when it reduces nothing. Nothing is listed as retained: what is retained is everything not named.

Acceptance is not a test plan in the generic sense, although it decides what the regression plan requires. A plan states what must be shown; an accepted reduction is what need no longer be shown, and no run can show that a loss is acceptable. So KAAL states no Acceptance Plan in `plans/`: its runs would require nothing and demonstrate nothing. What makes an acceptance more than a written waiver is what can be read from the files: the reduction it names really happens, it is exact, it is made for this candidate against this accepted state, and it says why. Whether the reason is good enough is the judgement of whoever accepts the candidate; KAAL does not make it, and does not infer it from the candidate causing the reduction. What still holds after the reduction is the regression's to show, by the accepted regression's cases for everything not accepted.

A replacement is two independent decisions. Feature names the successor as a new promise and requires it demonstrated; Acceptance names the loss of what it replaces. Neither implies the other: a demonstrated successor accepts no loss, and an accepted loss requires no successor. A Requirement moved to another place is the same pair under KAAL's identity by place. A Requirement rewritten in place cannot be accepted: its meaning would change at a place that seems to keep it, and a Requirement never changes; the new meaning is a new Requirement, newly promised, and the old one's loss is accepted. Requirements themselves never change for this: an accepted loss leaves the old Requirement as history.

The regression plan's own record of what it replaces and withdraws is, for the decision to stop requiring something, now the acceptance records' role; its BRAIN successors still state what a commitment means now. The next regression can be derived without guessing: what the accepted regression protects, less exactly the reductions its candidate accepted, with what the candidate newly promised and demonstrated.

What is left open: a case the candidate no longer keeps is not named as a reduction, since KAAL cannot yet tell a case removed from one moved or merged, and the accepted regression's own cases still judge the candidate itself. The data the Regression Plan provides is not yet read as protection. Nothing yet requires that acceptance hold before a candidate is accepted: the accepted regression's checker still refuses every commitment lost without a BRAIN successor, accepted or not, until the regression is derived from acceptance.
