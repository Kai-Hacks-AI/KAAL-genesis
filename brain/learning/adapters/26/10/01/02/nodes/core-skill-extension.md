name: core-skill-extension
---

KAAL separates three placements of machinery, Core, Skill and Extension, because the words core, adapter and composition were being used for them without a stable distinction, and the distinction had to be earned from the code KAAL has before more machinery is built. The records are in the Change adapters/26/10/01/02; this node records what was found and why the shape is what it is.

The evidence is the import graph. No Skill imports another Skill, imports anything under scripts/, or runs Git or names GitHub, so a Skill already is independent and the rule only states what holds. Everything under scripts/ depends on Skills, on other modules there, or on neither, and never in a cycle. One module, Genesis, imports Skills only, and nothing imports it. The vocabulary was tested on real examples and not by folder. Genesis is Core, and Testing, Managing Requirements, Managing Change, Using Seals and the others are Skills. The composition that derives a Plan's required instances from Requirements, born in #158, is an Extension in its composing role, since it relates two Skills that must not know each other. The Git boundary and the GitHub boundary are Extensions in their boundary role, and so will the environment boundary be, which does not exist yet. The two sealing and admission modules show why a role is never read from a file: pull-request-sealing.ts and seal-guard.ts hold KAAL's sealing policy and, in one function or a few calls, Git's mapping of a pull request to Changes, so one file plays both roles and only a function is one or the other.

The question was whether composing Skills and realizing a boundary belong under one concept, and they do, for one reason that also bounds the claim. What defines an Extension is not what it depends on, which differs, but what it keeps out of Skills: KAAL's combination of them, or an external system's facts. One rule places both, so that every Skill stays closed. They are not one interface, as the adapters records already said of adapters, and they are not both optional or both required, since an Extension is a placement. The unity would fail the day one role needed a dependency rule the other forbids, for example boundary Extensions that must be swapped at run time while composing ones cannot; nothing in KAAL does today.

Genesis is where the vocabulary is thinnest. By what it composes, Core is indistinguishable from an Extension, since it composes Skills into KAAL-specific behaviour. It is Core only because it is first: it runs in an empty place and presupposes no KAAL, while extending presupposes one, and its rule, depending on Skills only with nothing depending on it, is real and tested. Core is therefore a placement and not a third kind of capability, and importance does not earn it: sealing and Testing are needed by KAAL and are not Core.

Earlier records are immutable and use KAAL core for KAAL's own meaning on its side of a boundary, adapter for an Extension in its boundary role and composition for the composing role, so Core now names only the machinery that births KAAL. The vocabulary classifies machinery, never material: BRAIN, Changes, Requirements and Architecture records are born or placed by machinery, and the Agent uses KAAL and is none of it.

Not decided, and seen while earning the rules. Testing's observeConditions reads the host's platform to state a Run's conditions, which is Testing's own concept and is the edge the environment Extension will meet. Several Skills repeat the portable-path rule that names Windows reserved device names, and that is a property of their inputs, not a dependency. Skills export KAAL's directory names as defaults, change and brain/learning, so a relocated layout such as a .kaal/ root would have Extensions pass roots in. None of these is changed here, and the environment Extension, the Git and GitHub boundaries and the folder layout are not touched.
