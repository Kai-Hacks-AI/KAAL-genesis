KAAL separates three placements of machinery, Core, Skill and Extension, and keeps the operation that births KAAL apart from all three, because the words core, adapter and composition were being used for them without a stable distinction, and the distinction had to be earned from the code KAAL has before more machinery is built. The records are in the Change adapters/26/10/01/02; this node records what was found and why the shape is what it is. The target it is measured against is a clean repository holding KAAL under a .kaal/ root with brain, core, skills and extensions, installed by an operation such as kaal init. That is context, not scope: nothing is moved here.

The evidence is the import graph. No Skill imports another Skill, imports anything under scripts/, or runs Git or names GitHub, so a Skill already is independent of Skills, Extensions and providers, and the rule only states what holds. It does not forbid a Skill depending on Core, which is the target: six Skills each carry the same portable-name rule, and three carry identical id and front-matter handling, with no shared foundation to hold it. That duplication is the real pressure for Core, and it is why the current import graph must not be read as prohibiting Skill to Core merely because no Core is installed yet. Everything under scripts/ depends on Skills, on other modules there, or on neither; that graph is acyclic today, which may be only where code happens to sit, and is an observation and not a rule. Dependencies between Extensions are therefore left undecided until a real case needs one.

The vocabulary was tested on real examples and not by folder. Testing, Managing Requirements, Managing Change, Using Seals and the others are Skills. The composition that derives a Plan's required instances from Requirements, born in #158, is an Extension in its composing role, since it relates two Skills that must not know each other. The Git boundary and the GitHub boundary are Extensions in their boundary role, and so will the environment boundary be, which does not exist yet. The two sealing and admission modules show why a role is never read from a file: pull-request-sealing.ts and seal-guard.ts hold KAAL's sealing policy and, in one function or a few calls, Git's mapping of a pull request to Changes, so one file plays both roles and only a function is one or the other.

The question was whether composing Skills and realizing a boundary belong under one concept, and they do, for one reason that also bounds the claim. What defines an Extension is not what it depends on, which differs, but what it keeps out of Skills: KAAL's combination of them, or an external system's facts. One rule places both, so that every Skill stays closed. They are not one interface, as the adapters records already said of adapters, and they are not both optional or both required, since an Extension is a placement. The unity would fail the day one role needed a dependency rule the other forbids, for example boundary Extensions that must be swapped at run time while composing ones cannot; nothing in KAAL does today.

Core is the foundation Skills and Extensions depend on, and it depends on neither. It holds only what more than one of them needs and no Skill owns as its own semantics, never a composition and never an external system's facts, and importance does not earn it: sealing and Testing are needed by KAAL and are not Core. No Core is installed today. Genesis is not it. Genesis composes Skills to birth BRAIN and an Agent entry point, which is the operation of bootstrapping and not a placement within the installed KAAL; it is scaffolding for evolving this repository, it is evidence for the eventual kaal init, and it need not survive a clean birth. Keeping the operation apart from Core matters because one piece of code doing both kinds of work is exactly how they would be conflated. An earlier revision of this learning defined Core by operating before KAAL exists and by nothing depending on it; both were the properties of Genesis and not of a foundation, and review corrected them.

Earlier records are immutable and use KAAL core for KAAL's own meaning on its side of a boundary, adapter for an Extension in its boundary role and composition for the composing role, so Core now names only the shared foundation. The vocabulary classifies machinery, never material: BRAIN, Changes, Requirements and Architecture records are born or placed by machinery, and the Agent uses KAAL and is none of it.

Not decided, and seen while earning the rules. What moves into Core first, and where its edge is, is not earned. Whether Extensions may depend on one another is not earned. Testing's observeConditions reads the host's platform to state a Run's conditions, which is Testing's own concept and is the edge the environment Extension will meet. Skills export KAAL's directory names as defaults, change and brain/learning, which the .kaal/ layout would pressure. None of this is changed here, and the environment Extension, the Git and GitHub boundaries, Core itself and the folder layout are not touched.
